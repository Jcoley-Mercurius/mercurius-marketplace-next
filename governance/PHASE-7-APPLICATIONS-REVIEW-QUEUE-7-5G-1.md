### 2.1 The reader

`STABLE`, `SECURITY DEFINER`, `search_path = ''`, guarded by `vendor_require_operator()` (admin, `42501`). Execute is revoked from `public`, `anon`, `authenticated` and `service_role`, then granted to `authenticated` only. It returns `{checked_at, items}` with items `{application_id, since}` (R-4), ordered by `created_at`, then `id` (C-3).

An application is listed when its status is not `abandoned`, `rejected` or `approved`, no `vendor_onboarding` row for its `contractor_id` is `rejected`, and no `vendor_onboarding_review_starts` row exists for it. That is a conjunction of `applicationQueueState`'s exclusions, so its result does not depend on the order in which the page tests them:

| Page precedence (`applicationQueueState`) | Server |
|---|---|
| 1. `abandoned` | excluded by status |
| 2. onboarding `rejected` or application `rejected` | excluded by status or by the onboarding row |
| 3. review started → in review / active / suspended | excluded by the review-start row |
| 4. `approved` without a review start → legacy approved | excluded by status |
| 5. anything else → awaiting review | listed |

The page's `checking` and `unavailable` states exist only in the browser and are outside parity (C-2). A null `contractor_id` matches no onboarding row on either layer. A linked onboarding row without a review start does not count as a started review on either layer. `status` is `NOT NULL`, so `not in` never drops a row on a null.

`since` is `vendor_applications.created_at`: the time the application was received (R-3). It is not the start of a review episode, and an intake revision (a new `vendor_application_versions` row) does not change it.

## 6. Implementation decisions for Codex

| ID | Choice | Reason |
|---|---|---|
| I-1 | Only `postgres` and `authenticated` hold execute on the reader; `service_role` does not, unlike the summary | Matches `vendor_onboarding_intake_status`, the readback it mirrors; nothing server-side calls it |
| I-2 | The guard is `vendor_require_operator()`, not `private.require_admin()` | It is the guard of the applications readbacks this mirrors; both require the admin role |
| I-3 | The parity fixture projects three fields of `vendor_onboarding_intake_status` (`onboarding_status`, `review_started`) plus the row's `status` | They are exactly the inputs the page passes to `applicationQueueState`; the readback's other fields hold random ids and would make the fixture unrepeatable |
| I-4 | SQL 133's fixture times are absolute | The queue has no clock logic, so the parity fixture needs no normalization |
| I-5 | Later onboarding outcomes (`active`, `suspended`, `rejected`) and one closure are written as the owner in replica mode, after the real start commands | The outcome commands need evidence this queue does not read; only the resulting status matters, as in the 7.5C precondition method |
| I-6 | The R0 existing-provider start is not exercised | The reader tests only whether a review-start row exists, and that path writes the same table (`20261003001000:98`). SQL 133 uses the reviewed start and the recovered pipeline's begin-review |
